讨魔旅人 Questers

代码更改需求文档 v1.2

1. 文档目标

本次改造的目标不是推翻当前玩法骨架，而是把现有 demo 从“单文件可玩原型”升级成“可持续扩展、可承接正式美术资源、可继续做职业与内容系统”的正式前端骨架。

1.1 当前版本的核心判断

当前 demo 已经具备：

* 主菜单
* 地图推进
* 战斗循环
* 手牌渲染
* 奖励 / 商店 / 营火 / 奇遇弹层
* 敌人、遗物、状态词条的基础规则

所以当前最优先的工作，不是继续堆新玩法，而是先完成：

1. 视觉方向统一
2. 资源驱动接入
3. 角色选择正式落地
4. 前端结构拆分
5. 正式卡池逐步替换程序生牌

1.2 当前确认的视觉方向

本项目 UI 与表现层的正式方向，已经从旧版深色暗金奇幻 UI，切换为：

教堂彩窗 + 90 年代赛璐璐奇幻动画融合风格

这意味着后续所有前端实现都必须围绕以下锚点展开：

* 教堂彩窗的分区结构
* 铅条 / 黄铜骨架式边框语言
* 宝石透光与彩色玻璃分块
* 90 年代 OVA 时代赛璐璐角色层
* 更强的仪式感、圣像感、奇幻宗教感
* 角色永远是主视觉，UI 是前景功能层

现阶段默认主用 UI 目录为：

* `UI/教堂彩窗赛璐璐/`

旧版深色暗金 UI 已从当前资产目录清理，不再作为主流程默认风格继续扩展。

1.3 核心实现目标

1. 建立 角色层 / 背景层 / UI层 / VFX层 的分层渲染结构。
2. 建立 资源配置驱动 的角色、卡牌、背景、UI 皮肤接入方式。
3. 建立 场景管理 + 渲染器 + 状态管理 的代码边界。
4. 让角色选择、战斗 HUD、弹层系统全面切换到“教堂彩窗赛璐璐”视觉语言。
5. 让当前 demo 可以继续承接三职业入口、正式卡池、章节内容与更多场景资源。

⸻

2. 当前代码问题归纳

2.1 视图、逻辑、资源耦合过高

当前 HTML 中同时包含：

* 大量场景 DOM
* 大量样式
* 事件触发
* 业务逻辑
* 卡牌生成与战斗逻辑
* overlay 控制

这使得后续一旦接入正式 UI、美术资源、角色选择和更多事件模板，修改成本会迅速上升。

2.2 战斗表现层仍是原型态

当前战斗区：

* 我方已改为从 `assets/characters/<role>/` 下的正式角色资源选择战斗立绘
* 敌方主体仍由 `enemy-avatar` 文本 / emoji 驱动
* 背景主要依赖渐变和透视网格
* VFX 仍是几何 slash / flash 原型

这和你现在要的“教堂彩窗 HUD + 赛璐璐角色层 + 正式背景板 + 仪式感界面”还有明显距离。

2.3 卡牌渲染还没有正式资源接入口

当前卡牌已经有：

* 费用结晶
* 名称
* 稀有度边框
* 类型角标
* 描述区
* 关键词标签

但卡面中心仍然更接近图标占位，而不是真正的插画容器。手牌仍由 `generateCardHTML()` 直接生成并挂点击逻辑，不适合长期扩内容。

2.4 角色选择尚未正式接入

你已经有角色选择方向图和对应 UI 资产，但当前运行版本仍是：

* 固定初始牌库
* 固定主角资源
* 开局直接进入遗物三选一

这意味着三职业入口、职业卡池、职业配色和角色 UI 细节，都还没有进入正式流程。

2.5 交互事件分散

当前主菜单按钮、地图按钮、结束回合、牌堆查看、overlay 关闭等，既有 HTML 内联 `onclick`，也有 JS 运行时 `el.onclick`。

这会导致后续组件化和自动化测试都困难。

⸻

3. 总体改造原则

3.1 保留玩法骨架，优先重构表现层与接入层

不建议推倒重写。

当前已具备的流程骨架都应该保留：

* 场景切换
* 地图推进
* 战斗状态更新
* 手牌渲染
* overlay 体系
* 卡牌生成与部分战斗数值逻辑

优先重构“渲染方式、资源接入方式、角色入口、UI 语言”。

3.2 所有视觉实现改为“资源驱动”

未来角色、背景、卡牌、UI 都必须通过配置切换，而不是写死：

* 根目录角色占位图
* emoji 敌人
* CSS 渐变假背景
* 某个按钮直接写某一张图

3.3 所有新界面默认使用新 UI 目录

新做页面、战斗 HUD、角色选择、弹层、商店、营火、图鉴面板，默认优先使用：

* `UI/教堂彩窗赛璐璐/`

避免新旧风格混用。

3.4 可读性优先于装饰密度

虽然 UI 风格升级为“教堂彩窗 + 赛璐璐”，但必须坚持：

* 数值优先可读
* 卡费优先可读
* 血量 / 护盾 / 状态优先可读
* 角色主体优先于 HUD
* 手牌区不能因为花纹过多而失去扫描速度

⸻

12. 事件系统改造需求

12.1 当前问题

代码里存在两类事件绑定：

* HTML 内联 `onclick="..."`
* JS 运行时 `el.onclick = ...`

这会让重构后的组件边界不稳定。

12.2 改造要求

统一改为：

* `bindMenuEvents()`
* `bindBattleEvents()`
* `bindOverlayEvents()`
* `bindMapEvents()`
* `bindRoleSelectEvents()`

所有按钮通过 `data-action` 或显式查询后 `addEventListener` 绑定。

12.3 禁止项

* 不再新增新的 HTML 内联 `onclick`
* 不再在渲染函数中夹杂业务逻辑
* 不再让视图模板直接知道 battle rule

⸻

* `vfx-p-def`
* `vfx-e-atk`
* `vfx-e-def`

14.2 改造方向

保留机制，替换表现。

角色动作

* 位移幅度更小
* 用 pose 切换代替大幅缩放
* 敌人攻击不宜继续用“emoji 前冲”

特效

* 使用手绘 slash 贴图 / 法阵贴图 / 光束贴图
* 特效层级在角色上、UI 下
* 单次技能特效时长控制在 300–800ms

伤害反馈

* 数字出现
* 角色轻微受击位移
* 短促闪白
* 接触点火花

17. 风险点

17.1 最大风险

不是玩法，而是资源接入后布局崩坏。

因为当前很多位置使用固定像素：

* 玩家区
* 敌方区
* 手牌区
* pile 区
* 结束回合按钮

正式立绘、彩窗 HUD、卡图接入后，很容易发生遮挡。

17.2 第二风险

战斗状态和 DOM 深度耦合。

例如抽牌、手牌渲染、状态更新、浮字和 VFX 都会直接碰 DOM。

17.3 第三风险

继续边开发边往单文件里追加内容，会让重构窗口越来越难。

17.4 第四风险

新 UI 装饰性更强，如果不提前建立统一规范，会出现：

* 角色选择一套语言
* 战斗 HUD 一套语言
* 弹层又是另一套语言

最终会失去“这是同一个游戏”的整体感。

⸻

18. 详细验收标准

18.1 角色选择

* 开局先进入角色选择
* 三职业可以正式选择
* 每个角色有独立标签、说明、配色与初始卡组
* 角色选择页完整使用新 UI 风格

18.2 战斗界面

* 我方角色始终为背面 / 背侧立绘
* 敌方角色始终为正面 / 3/4 正面立绘
* 背景可配置切换
* 战斗 HUD 使用彩窗赛璐璐风格
* 战斗 UI 不压角色主体
* 特效不会盖住主要文字信息

18.3 卡牌

* 卡图支持正式插画
* 卡框支持按稀有度 / 职业切换
* 手牌排布在 5–10 张情况下都稳定
* pile 预览使用静态卡样式
* 程序生牌不再是正式内容主来源

18.4 工程

* 无新增内联 `onclick`
* 场景切换统一走 manager
* 角色、背景、卡图、UI 都通过 registry 配置
* 资源加载失败时有 fallback 图
* 主代码不再依赖单 HTML 大脚本

18.5 风格结果

最终画面要同时满足：

* 角色在前景
* 背景是静态板
* UI 是前景功能层
* 结构语言能看出教堂彩窗与黄铜骨架感
* 角色仍保有 90 年代赛璐璐奇幻动画的主视觉地位
